## 1. Why this feature

Six of the alpha's seven prerequisites are met or settled; this is the last, and the only one with a one-sentence definition and no price. The roadmap's *Launch readiness* (`:283`) names three things — admin/moderation, anti-grief tooling, an economy-health view — and says why: *PvP + a real economy create exploit surface*. The alpha has neither. Combat is excluded (A), so the only griefs left are the ones a sandbox of gatherers, crafters and traders can do to each other: flood a channel, pick a bad name, loot a body after the grace window (which is the death contract, not grief), and camp a node (which is the economy, not grief). Evennia 6.1.0 already answers the first two (`boot`, `ban`, `channel/boot`, `MAX_COMMAND_RATE`; *Rev 3:* not `channel/boot`, which crashes — LM3), and the alpha's own design answers the other two.

What the alpha cannot do today is **remember what happened in it**. The currency ledger (`world/economy_log.py`) records mint and burn and nothing else — by design, it guards an invariant. A trade completes by assignment (`world/barter.py:578`), a craft consumes its inputs (`world/crafting_base.py:431`), a forage yields, a corpse crumbles (`typeclasses/corpse.py:165`), and none of it leaves a line anywhere. The persistent instance's whole purpose (roadmap (D3)) is *so that prices can emerge* (*Rev 2:* narrowed by roadmap (G) to operations and onboarding — the log is built anyway, so the economy milestone has it from the first day); BACKLOG *Seasonal supply & population memory* waits on *two game-months of ledger data*; and the ledger it waits on holds no prices. So the minimum of *faucet-vs-sink view* is not a view at all: it is the log the view would read, written during the alpha and read after it. That is the feature. Everything else here is making sure the door is locked (registration), the room is lit (runbook), and the box exists (instance).

## 2. Decisions locked 2026-11-01 (LM1–LM11)

**LM1 — The minimum is measurement, not moderation.** Of `:283`'s three parts, *admin/moderation* and *anti-grief* are met by Evennia's shipped commands and settings, verified live and written into a staff runbook (LM3); *faucet-vs-sink view* is **new code**, scoped as an **activity log** — one line per economic event, written by the code that performs it, read offline after the alpha. Rejected: the full `:283` entry (it prices a PvP opening the alpha is not); nothing new (an alpha that cannot report a single price has not tested pillar 1, whatever the cohort says it felt). `@economy` stays as it is: the money-supply view, Developer-locked (`commands/currency_commands.py:416–481`).

**LM2 — The log is a file of JSON lines, appended synchronously, never the database.** One file, `server/logs/activity.jsonl` (under `settings.LOG_DIR`, `settings_default.py:183`), one object per line, written by `world/activity_log.py::record(kind, actor, **fields)` with a UTC timestamp, the game-time stamp (month/day, so seasons can be read back), the actor's dbref and key, the room's dbref, and the kind's own fields. **Kinds** (the sites found live, §3): `gather` (forage, harvest), `craft` (inputs consumed, product, quality), `dismantle`, `trade` (both parties, both sides, both coin amounts — the only price datum the alpha produces), `work` (faucet payout, task, copper), `consume` (eat, drink), `repair`, `knowledge` (learn, teach, inscribe, scribe — pillar 1's second market), `crumble` (corpse and its contents), `improve` (skill, from, to — which makes BACKLOG *Scribe teaches Craft with no difficulty datum*'s trigger readable). The decision session said *via `evennia.utils.logger.log_file`*; read at source that function writes from a thread pool (`utils/logger.py:557–580`, `deferToThread`) and rotates the file at `CHANNEL_LOG_ROTATE_SIZE` (1 MB, `settings_default.py:198`) copying the last `CHANNEL_LOG_NUM_TAIL_LINES` (20) into the new file (`:439–470`, `:516–550`), so a reader would meet duplicated and possibly reordered lines. The lock's substance stands — a file, not a DB script; offline analysis; no in-game reader — and the writer is a plain synchronous `open(path, "a")` append on the reactor thread, which at this scale costs microseconds and keeps the file in event order with no rotation. Size at ten players is megabytes, not more; the file is one of the things L6.2 backs up. A write failure is logged with `log_err` and never aborts the event (observation must not change what it observes — the opposite of the ledger's ordering, and deliberately so). Rejected: a second `EconomyLedgerScript`-style DB store (unbounded attribute growth, and a `_SaverList` of ten thousand dicts is the wrong shape for a question asked once); an in-game `@activity` command (a report over a file is a Python script, not a command).

**LM3 — No new admin commands; a runbook instead.** Evennia 6.1.0 ships `boot` (Admin), `ban`/`unban` by account, IP or subnet with a reason, persisted in `ServerConfig` `server_bans` and checked at login (`accounts/accounts.py:637, 737, 1065`), `@accounts/delete`, `userpassword`, `wall`, `emit`, `perm`, `channel/boot|ban|unban|lock`, flood control (`MAX_COMMAND_RATE = 80`, `settings_default.py:278`) and per-IP creation and login throttles (`:838–841`). Each is verified **live from a second, Admin-permission account** in L4.1's protocol, and the runbook records the exact line, what it printed, and what the player saw. Nothing is verified by reading its docstring (lesson 196). *(Rev 3, verified live in L4.1: `channel/boot` and `channel/ban` crash in 6.1.0 before they change anything — `comms.py:632` reads `nick.value` on the tuples `nicks.get(return_tuple=True)` returns, and `channel/ban` reaches it through `boot_user` at `:663` — so channel moderation is account-level for the alpha (`boot`, `ban`) and BACKLOG *Channel boot/ban crash upstream* owns the rest. `ban` refuses the next login and does not disconnect, so the runbook boots after a ban. `@accounts/delete` is Admin-locked but checks Developer inside, and leaves the character behind.)*

**LM4 — Registration is closed at all three doors.** `NEW_ACCOUNT_REGISTRATION_ENABLED = False` (`settings_default.py:40`) stops `create` (`commands/default/unloggedin.py:178`) and the menu login the project runs (`contrib/base_systems/menu_login/menu_login.py:93`; `CMDSET_UNLOGGEDIN` in `server/conf/settings.py`). It does **not** stop the website: `web/website/views/accounts.py:33–70` (`AccountCreateView.form_valid`) creates the account without reading the setting — only the template hides the form (`templates/website/registration/register.html:30`, `web/utils/general_context.py:72, 126`), and the route is live at `web/website/urls.py:20`, which the project's `web/website/urls.py` includes unchanged. So L1.2 builds the project's URL list **without** `auth/register`, and its test is a Django-client POST that gets 404 and creates nothing. Accounts are made by staff (`evennia.utils.create.create_account`, `utils/create.py:240`) per LM7. Rejected: an invite-code system (code nobody needs for eight people); turning the website off (the cohort is on phones — Character Creation CC6 — and the web client is the reason the site exists). *(Rev 3: built otherwise at L1.2, decisions B, B1 and c. A filtered route would have failed twice: Evennia's `login.html:41` reverses `{% url 'register' %}` unguarded, so dropping the name breaks the login page; and the project's `web/urls.py` appends Evennia's root patterns, which include `evennia.web.website.urls` a second time, so a route filtered out of one include is still served by the other. The project instead routes `auth/register`, same path and name, first to `GatedAccountCreateView` (`web/website/views/accounts.py`), which answers 404 while the setting is off — one knob for every door — and keeps Evennia's login-page link (B1). The project's `CMDSET_UNLOGGEDIN` is the menu_login contrib, whose cmdset installs no telnet `create`, so the first door is tested through the menu (`menu_login.py:93`) and a test pins that `create` is not installed (c). Staff make accounts with `Account.create`, LM7.)*

**LM5 — One decomposition, and the instance is its last component.** BACKLOG *Persistent alpha instance* says *decided together*, and it is: L6 is the instance, after L5's merge, because moderation and measurement mean nothing on a box players cannot reach, and because every L1–L4 task is first proved on it. The entry's trigger fired on `d5450ad` (prerequisites 1–5 and 7 on `main`, *Death contract surfaces* since `123ac53`) without the entry being touched — the pattern of lesson 195 — and goes BLOCKED → SCHEDULED (L6) in this commit. *Public test server* (b), the nightly-wiped smoke box, is unchanged and still waits on Stage 5; L6's runbook is what (b) will copy.

**LM6 — Hosting and operations.** A small VPS in the EU, not a home IP (the entry's constraint, inherited from *Public test server*); Ubuntu LTS; a venv with `evennia==6.1.0` from the `requirements.txt` L1.1 adds; a `systemd` unit that runs `evennia start` as an unprivileged user and restarts on failure; **SQLite stays** — the assumption is a cohort of ten, and a database engine change is a migration with no benefit at that size (revisited only if L6.3's smoke test shows lock contention); a daily off-box backup of `server/evennia.db3` (taken with `sqlite3 .backup`, not a file copy of a live database), `server/logs/activity.jsonl` and `server/logs/*.log`, 14 days' retention; Evennia's own log rotation as shipped (`SERVER_LOG_DAY_ROTATION = 7`); deploys are **tagged commits on `main`** (`alpha-YYYYMMDD`) applied as `git fetch && git checkout <tag>` → `evennia migrate` → `evennia reload`, with `evennia reboot` only when settings change; **no GameGold wallet, key or chain node on the box**, and no Treasury mint until the cohort contract names an amount. The provider, the DNS name and the user names are Adam's and live in the runbook, not here. Rejected: a home server behind a tunnel (the IP is hidden but the constraint is about what a home box is, not what it shows); a PaaS (nothing at this scale it does that `systemd` does not).

**LM7 — The cohort contract.** **Accounts:** staff creates each one with `create_account(username, email, password, permissions=["Player"])` and a one-time password sent out of band; the player changes it with `password` on first login; `MULTISESSION_MODE 0` and `MAX_NR_CHARACTERS 1` stay as shipped (`settings_default.py:798, 817`), so one account is one character made through chargen. **Size:** 8–10 invited, planning for about five active *(Rev 2: one to three humans is the realistic case, roadmap (G); automated test players are accounts made the same way, LM10)*. **Schema during the alpha:** additive and migration-free (no-backfill, CC7's rule); a change that cannot be made that way is a **wipe announced at least seven days ahead** on the connection screen and in `help alpha`, never a migration of cohort characters. **What the player reads:** `help alpha` (a file-help entry in `world/help_entries.py`, the precedent of `help death`), pointed to by the connection screen; it says in order that the world is wiped at close-out, how death works (`help death`), that every economic act is logged for analysis, that GameGold is not part of the alpha and nothing minted is a promise of value, and how to reach staff. No separate site, no form, no NDA. *(Rev 3, found live in L4.1: `create.create_account` skips password validation, the default channels and the character, so staff use `Account.create(username=…, password=…, permissions=…)` (`accounts/accounts.py:999`), which returns `(account, errors)` and makes the character at once, as a statue in Limbo, joined to Public; runbook §1.)*

**LM8 — Launch blockers in and out.** **In (L3):** *Evennia is not pinned in the repo* (`:2628`, trigger *the persistent alpha instance*) → L1.1; *Worn clothing leaves without `remove()`* (`:1632`, *before the persistent alpha instance*) → L3.1; *`recipes` lists floored recipes under "can craft"* (`:2204`, re-armed to this decomposition at Rev 58) → L3.2; *World-loot scroll seed* (`:771`, *before the first cohort of real players logs in*) → L3.3, reshaped by LM9. **Out, triggers unchanged:** *A trade that carries a party across the limit sends no crossing line* (`:1655`, cosmetic, the ceiling holds); *Dev characters keep a float `health.base`* (`:1021`, never, since the database is wiped); *Free Skill Points* (`:935`, close-out data); *Ledger `actor` field* (`:2782`, Component F); *`@economy audit` counts the Treasury as a holder* (`:2799`); *Article and number in messages* (`:2186`). **Out, re-triggered:** *System Map describes the world as of Stage 4* (`:2642`) moves from *before the alpha opens* to **the Stage 5 design session**, which is the first reader that needs the map and the first session with time to draw it; nothing the cohort does reads it. **Annotated:** *Seasonal supply & population memory* (`:1803`) — its *two game-months of ledger data in `world/economy_log.py`* means the activity log from now on; *Scribe teaches Craft with no difficulty datum* (`:573`) — the `improve` kind is the log it asks for.

**LM9 — The scroll seed is a launch requirement, and a test keeps it one.** Recomputed against `world/recipes.py` (29 recipes, 17 `requires_knowledge = True`) and `world/professions.py:66–70` (four professions, five grants): `cloth` and `leather` have two grantors, `linen shirt` and `leather boots` one, and **hood, scrollcase, bandolier, breeches, sack, backpack, shoes, robe, reversible clothes, linen cuirass, saddlebag, bone armour and tent have none**. Profession grant is the only bootstrap (BACKLOG `:779–780`: reverse-engineering needs a crafted item, and scroll, book and teach need a sender who knows the recipe), so thirteen of the alpha's learnable goods — including the tent, the alpha ladder's rung-60 anchor — are **fountains**: a sink with no source, in the Source/Sink Ledger's own word. Alpha Content B5 partitioned them, CC6 kept four professions, and neither counted. **Decided:** L3.3 seeds **one stamped scroll per knowledge-gated recipe with fewer than two grantors** — fifteen scrolls — into the seeded world through `world/seeding.py`'s own idempotent path (a `seed_id` of `alpha.scroll.<recipe>`, `find_seeded` before `spawn`, `Scroll.stamp` for identity), consumed by `learn`, **replenished by staff on request** (a runbook line; the *one-shot vs respawn* decision the entry asks for is answered *manual, for the alpha*), and a test pins that **every `requires_knowledge` recipe has at least one source** — a profession grant or a seed row — so the next recipe batch cannot ship a fountain. The first player to learn the tent is the cohort's only tentmaker until five crafts let them teach (MD5): that is pillar 1 as designed. Rejected: extending the professions so every recipe has a grantor (a chargen-data design — who gets the tent? — filed post-alpha, triggered by close-out data showing what was actually learned — *Rev 2: re-anchored to the economy milestone, roadmap (G5)*); un-gating the thirteen (undoes B5 and the knowledge market with it).

**LM10 — Close-out criteria** *(Rev 2, roadmap (G): the alpha measures operations and onboarding; Rev 1's fifty trades and fourteen-day early close are dropped)*. A game-month is 28 game-days at `TIME_FACTOR = 4`, so seven real days; a season is three real weeks. The alpha closes when **eight real weeks** have passed since the instance opened (about eight game-months, so at least two season boundaries — the time systems are part of what has to run) **and** each of five checks holds, every one read from a file or a receipt rather than from mood: **(1) no lost state** — no incident in which a player lost something the game's own rules did not take (death, decay and a trade are rules; a crash, a bad deploy or a restore that rolls a player back are not), each incident written into the runbook as it happens; **(2) a live restore** — L6.2's rehearsal repeated on the box at least once while the alpha runs, not only before it opens; **(3) a live deploy** — at least one tagged deploy applied to the running instance by L4.1's sequence, without a wipe; **(4) tracebacks accounted for** — every traceback in `server/logs/` since open has a fix on `main` or an entry in `docs/BACKLOG.md`; **(5) onboarding unaided** — at least one human who is not staff goes from chargen to a first `craft` line in the activity log with no help from staff beyond what `help` says (asked of the player: the log cannot say it). There is **no early close**: automated accounts log in, so any login rule would be met by them, and an alpha with no humans still measures (1)–(4). **Automated test players** are accounts made per LM7, listed by account and character dbref in the runbook (L4.1), and removed from every reading of the log offline: a line is dropped when any party's dbref is on the list — a trade between a human and an automated player too — and the report runs over the filtered copy, so the instance runs no code for them. `evennia --dummyrunner` is never one of them: it logs in with `create`, which L1.2 closed, and its settings mixin grants every account Developer and lifts the creation and login throttles (`evennia/server/profiling/dummyrunner_settings.py:123, 137`, `settings_mixin.py:20, 22–24` at `v6.1.0`; *Rev 3*, corrected from `:20–22`); it runs against a scratch copy of the game dir only. Close-out is: copy `activity.jsonl`, the ledger (`@economy audit` output) and a `sqlite3 .backup` off the box; filter the automated actors out and run L2.3's report over the copy; write (1)–(5) with their receipts into the roadmap's alpha entry; then wipe, as the contract says. The GameGold trigger is no longer set here (roadmap (G4)). The numbers are the floor that makes the alpha worth closing, not a target; the roadmap's alpha entry carries them.

**LM11 — Order, and unnumbered.** L1 (pin, registration) → L2 (the log) → L3 (blockers) → L4 (runbook, `help alpha`) → L5 (merge) → L6 (the instance opens on a tag). Code before the instance, because every task is proved on the box and a box that opens before the log exists spends cohort weeks producing nothing readable. The sixth prerequisite by decision (A), unnumbered for Rev 17's reason.

## 14. Consequences worth reading twice

- **The log changes nothing it observes.** A `record()` failure is swallowed; the ledger's ordering (write first, abort the money movement on failure) is the opposite rule for the opposite reason, and both are written down in their module docstrings so nobody harmonises them.
- **Fifteen scrolls is a one-time supply, by decision.** After the first `learn` of each, the recipe lives in players. If the cohort's only tentmaker leaves, staff reseeds on request; that is the respawn policy, and it is manual on purpose — an automatic respawn would be a free recipe faucet.
- **Thirteen fountains shipped unnoticed through three decompositions.** The source test is the fix; the lesson (207) is that a partition which gates access needs a count of the grantors on the same commit.
- **`NEW_ACCOUNT_REGISTRATION_ENABLED` is not what it says.** Two doors of three. The gated view is the project's (`GatedAccountCreateView`, Rev 3) and must survive an Evennia upgrade; L1.2's POST test is what notices if it does not.
- **The alpha has a date.** Eight weeks and LM10's five checks are written here and in the roadmap so that *when does it end?* is answered by reading, not by mood.
